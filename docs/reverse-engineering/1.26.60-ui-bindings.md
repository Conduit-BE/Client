# Runtime legacy UI binding count

Target: Minecraft Bedrock Windows GDK x64 **1.26.60.5**, package
**1.26.6005.0**, 2026-11-07. Exact executable SHA256
`1d6ad5c217e9305442c353ba3e9bca623d5719134e1cc8a84fb1233f7145e85c`,
identified by the existing standalone image guard. All RVAs are build-specific.

## Question and method

Count retained, instantiated legacy data-binding records belonging to the same
active screen as Elements. This is not a binding value inspector or a count of
unique binding names, evaluations, global providers, or JSON definition entries.
Reuse the verified [active screen](1.26.60-native-screen.md),
[owned control traversal](1.26.60-ui-controls.md), and component rank machinery.

Read existing findings first; they explicitly left binding storage unverified.
Used the existing matching Ghidra project with bounded PE-unwind function ranges
and `ConduitUiProbe.java`; no repeated whole-program analysis. String seeds:
`binding_collection_name`, `binding_condition`, `_populateDataBindingComponent`,
`_bind@DataBindingComponent`, `_addBindings@DataBindingComponent`.
The REA MCP session had no active binary; the established local Ghidra workflow
provided static evidence. Temporary observation used the existing bounded
Frida/Proton transport, without native function calls or binding writes.
Ignored excerpts and observation artifacts: `.local/re-investigation/binding-count-20261107/`.

## Confirmed static evidence

| RVA / field | Observation |
| --- | --- |
| `0xf5d051e`, `0xf5883d9` | Binding collection name and condition string literals. RIP references inside `0x1c8b460–0x1c8c3d6`. |
| `0x1c8b460` | UIControlFactory population path allocates a 0x60-byte component, assigns table `0xf0fc970`, stores owning control at +8, attaches it to that control, then populates binding records. Calls `0x1919b10`, `0x19191b0`, `0x1919500` for different binding paths. |
| `0x128f5e28` | DataBindingComponent's dynamically initialized component bit. Population reads this bit and ranks the packed control component array through popcount(mask & (bit-1)). Runtime observation found bit 2048; production reads/validates it, never hardcodes that value. |
| component `+0x10/+0x18/+0x20` | First owned vector: begin/end/capacity. |
| component `+0x28/+0x30/+0x38` | Second owned vector. |
| component `+0x40/+0x48/+0x50` | Third owned vector. |
| `0x1939be0–0x1939d82` | Component destructor independently destroys all three vectors, calling `0x1919810` once per **0x108-byte (264-byte)** record, then releases each allocation. |
| `0x1918f20–0x19190df` | Component clone independently traverses all three vectors with the same 264-byte stride and copies qualifying records into the corresponding vectors of the new component. This corroborates three owned record collections, not three references to one collection. |
| `0x1919500` | Constructs a binding record and appends it to the first vector, advancing end by 0x108. |
| `0x19192a0` | Shared binding/expression population path uses callback table `0xf0fd0c0`. |
| `0x19354f0` | Callback constructs a binding record and selects exactly one destination offset (+0x10, +0x28, or +0x40), then appends with the same 0x108 stride. Selection examines condition and native control/component context. No claim is made that these vectors correspond simply to three binding types or active/inactive states. |

Taken together, these observations establish retained binding **record** counts
as the sum of the three vector lengths divided by 264. Names repeated across
controls/instances are distinct records and contribute individually. No evaluator
is invoked, and no resolved-value representation is claimed established.

## Controlled runtime observation

A passive 20-second observer attached to the already-established natural legacy
scene/root name thunk `0x4cd2860`, rather than the installed screen-name hook.
It reused the verified owned child traversal, checked each candidate component's
exact table and owning control, and verified all three vector descriptors.
Callbacks ran on native UI thread 280 in this process. Observed:

| Screen root | Runtime controls | Binding components | Vector lengths summed by partition | Total records |
| --- | ---: | ---: | --- | ---: |
| `small_chest_screen` (BeHub) | 770 | 393 | 371 / 0 / 104 | **475** |
| `toast_screen` | 110 | 39 | 36 / 0 / 5 | 41 |

The toast sample demonstrates a separate hierarchy; it is **not added** to the
production active-screen total. BeHub's observation took 15 ms in instrumented
JavaScript, including control traversal; that is not DLL overhead. Examples of
real owning controls included `outer_left`, `inner_left`, `inner_right`, etc.
The probe detached normally with no reported crash, cleaned its owned helpers,
and left the game running. These values are observations, not test constants or
expected totals for every future screen/reload.

Confidence: high for the exact-build owned-vector layout and observed count.
Binding condition partition meanings, expression values, and full global/native
provider coverage remain outside this counter's scope.

## Production implementation and semantics

`src/core/binding_count.hpp` validates descriptor ordering, null representations,
record stride, capacity, overlap between partitions, and count overflow/limits.
It sums only active vector lengths, excluding unused capacity. A safety limit
produces an explicit incomplete count; a bad snapshot produces Unavailable.

`src/experimental/legacy_reload.cpp` reuses the deduplicated active-screen control
list already collected for Elements/factories. It does **not** walk the hierarchy
again. A separate phase has a 5 ms deadline, runs only after complete control
collection, and shares the existing once-per-second / screen-change sampling.
Elements and factory metrics survive binding-read failure. Per control it reads
the component mask, ranks the packed pointer array, checks exact component table
and owner, and copies descriptors twice to reject changes. Root/scene identity
is rechecked by the existing collector before any metric is published. No native
function is called, no lock is held while reading game data, no per-binding
allocation/traversal is performed, and all raw handles are cleared on callback
exit. Maximum descriptors are 65,536 records per vector; exceeding that limit
never becomes a misleading exact total.

The copied expiring `ScreenMetrics` snapshot includes bindings. Presentation adds
only `current screen.bindings` beside `elements`; no binding field is added to
factory rows. Controls created by factories are still part of the screen's
hierarchy and their bindings contribute to the screen total. Invisible controls
and retained bindings whose condition is currently false are included. Identical
names are not deduplicated. Native/controller bindings without a retained
DataBindingComponent record and HBUI DOM bindings are not covered.

No Frida is required by the DLL. No hook, rendering architecture, resource pack,
reload behavior, screen selection rule, or factory counting semantics changed.
A count of zero requires a successful complete sample; unsupported or invalid
samples show `Unavailable`, and limits show `>= N (incomplete)`.

## Validation

Portable tests cover empty/single/multiple vectors, changing record counts,
invalid ordering/stride/capacity/null descriptors, aliasing/overlap, safety limits,
overflow, unavailable reads, deadlines, and snapshot copy/expiry/invalidation.
The Windows overlay smoke verifies the binding count is placed between the
screen's Elements and Factories, with unchanged factory rows and F3 behavior.
Synthetic tests do not establish Minecraft layout correctness; the passive
observation above supplies separate native evidence.

Manual acceptance remains required: open HUD, pause, inventory, and BeHub;
compare different hierarchies; reload with Ctrl+R; confirm the screen-level count
updates, unavailable states are honest, FPS remains acceptable, and the game
stays stable. No release, tag, or push is authorized.

### Standalone confirmation

Relaunched through the user's configured automatic injection, with no Frida
attached. The rebuilt DLL logged complete counts on the verified UI thread:
HUD 973 controls / **526 bindings**, BeHub chest 770 controls / **475 bindings**,
and the separate two-control crosshair screen had a verified **0** bindings.
The chest total matches the independent passive observation. A viewport capture
also showed `bindings: 526` immediately below HUD `elements: 973`, with no binding
rows inside factory details. First combined control/factory/binding samples were
1,727 µs HUD and 1,451 µs chest; these are single samples, not a benchmark or a
zero-overhead claim. User acceptance across further screens/reloads remains open.
