## A — Root, static and live evidence

Reuse `SceneStack::get-name` candidate `0x56d000`, accepted native caller `0x65b0119`, and the verified game-thread gate. The stack's `+0x18/+0x20/+0x28` vector contains 32-byte scene entries. The selected scene is `[end-0x18]`. Only exact legacy scene table `0xf20ec60` is accepted for counting. Its screen view is `[scene+0x40]`, its VisualTree is `[view+0x50]`, and VisualTree shared root/owner are at `+8/+0x10`.

Static name thunk `0x4cd2860` and implementation `0x4cc7530` establish this root path. One bounded observational hook on that naturally called thunk captured the live `small_chest_screen` root on the same game thread already verified for screen detection/reload. The VisualTree table was `0xf2094c0`. The root has its runtime name at `+0x20`; it is a non-virtual control object, not an object with a vtable at offset zero. Its first two words represent its shared-from-this weak reference. Treating its first word as a virtual-method table would be incorrect.

## B — Descendants and ownership

Reused saved Ghidra 12.1.4 project `/tmp/conduit-ui-only-ghidra/LegacyUiOnly`, without whole-program analysis, using original PE unwind boundaries and `ConduitUiProbe.java` from [the existing tooling workflow](../../tools/reverse-engineering/README.md). Search seeds: `getControls@VisualTree`, `getVisibleControls@VisualTree`, known VisualTree table and root construction path. Original-bound selections and raw excerpts remain ignored in `.local/re-investigation/element-count-20261106/`.

| Function RVA | Observed role |
| --- | --- |
| `0x4c6edb0–0x4c6f049` | Creates replacement VisualTree; installs shared root at `+8/+0x10` with reference-count operations. |
| `0x4c6dba0–0x4c6dd2e` | Starts native predicate-driven traversal from `[tree+8]`. |
| `0x4c6d460–0x4c6d608` | Visits a control, obtains its shared ownership, then **unconditionally** descends immediate children from `control+0x98` through `+0xa0` in 16-byte steps. Predicate rejection affects output inclusion, not descent. |
| `0x4c6dd90–0x4c6de9c` | Separate traversal propagating visibility state, using the same child vector. Counting intentionally does not apply this filter. |
| `0x1ca2ee0` | Root ownership block disposal thunk: adds `0x10`, then jumps to control destructor `0x1c65f60`. |
| `0x1c65f60` | Destructor decrements each child entry's owner strong count at `owner+8`, invokes disposal on zero, then releases vector storage. It separately releases weak references at other offsets. |

Confirmed child representation: `control+0x98/+0xa0/+0xa8` is a vector descriptor (begin/end/capacity). Each entry contains `{control pointer, shared-owner pointer}` occupying 16 bytes. This is distinct from the component bitset at `+0xb0` and component storage at `+0xb8`; components/resources are not counted as additional controls. The destructor and native recursive collector establish **strong parent-to-child ownership**. A probable weak back-reference near `+0x88/+0x90` is not traversed or used; its exact parent semantics are not needed or claimed verified.

The inspected runtime samples form trees (`edges = controls-1`, no duplicate references). This is an observation about those samples, not a global graph invariant. The implementation supports shared descendants and cycles defensively.

## D — Client integration and semantics

The existing native name callback samples the same active scene, after the original name accessor returns and before its caller resumes. A synchronous traversal on that verified UI thread follows the selected root's **owned child edges only**. Root, scene and control addresses are local borrowed values; no address is retained after the traversal. Fixed scratch arrays are cleared on every exit. An atomic collection gate prevents overlapping use of scratch. There are no Minecraft native calls or Conduit locks inside traversal; guarded `ReadProcessMemory` copies fail safely. Changed vector descriptors or root/scene identity observed during the sample invalidate the result.

- Include the root and all instantiated descendants, whether visible or invisible.
- Count each unique control object once; ignore weak/parent references, components, textures, definitions, uninstantiated templates, background scenes and HBUI DOM nodes.
- Traverse at most once per second for an unchanged native screen name; a reported name change triggers an immediate new traversal at the existing name-sampling boundary (up to 4 Hz).
- Same-name reconstruction, collection edits and Ctrl+R are reflected by the next periodic sample. Identical counts after a reload are legitimate.
- Publish name, count status and collection duration atomically in the existing copied diagnostics snapshot. Counts are never paired with another screen's name; expiry/invalidation removes both.
- Fixed limits: 8,192 unique controls, 32,768 edges, and a **soft 5 ms traversal deadline**, checked between reads. There is no depth cutoff and no recursion. A budget limit produces `>= N (incomplete)`, not an exact total. Paging/OS read latency can overrun the soft deadline; this is not a hard real-time guarantee.
- Invalid/missing roots, failed reads and unverified scene/tree layouts produce `Unavailable`. Verified zero is a separate complete result supported by the generic algorithm; native missing-root cases are not reported as zero.
- Milestone A's title/Play limitations and split-screen exclusion remain. Ore UI names can still be shown, with Elements unavailable.

A maximum of four first-screen collection timing records is logged per process to validate cost. No per-frame/per-control logging is enabled. `src/core/control_count.hpp` owns the platform-independent algorithm; `src/experimental/legacy_reload.cpp` is the exact-version native adapter; `src/core/screen_metrics.hpp` carries copied results; the existing overlay changes only the Elements text binding.

### Standalone check

After a normal save/quit and fresh launch with automatic injection, the DLL operated without Frida and displayed the same complete totals: HUD 1,033, Pause 799, Inventory 4,643 and BeHub `small_chest_screen` 770. Bounded native diagnostics recorded collection times of 703 µs, 598 µs and 3,353 µs respectively for the first HUD/Pause/Inventory samples. A transient `hud_crosshair_screen` sample (2 controls, 86 µs) consumed the fourth logging slot; the BeHub cost was therefore not logged. No claim about worst-case overhead follows from these isolated samples.

Ctrl+R completed twice through the existing targeted backend, including while the BeHub interface was open; periodic counts continued at 770 after reconstruction. Selecting a different existing entry did not establish a control-count change; visibility/content changes may reuse existing instances. Dynamic additions/removals are covered synthetically, but actual collection-generation changes and sustained performance still require the user's checkpoint. No resource files or UI objects were modified by inspection. Automated results: 5/5 portable, 16/16 Windows/Wine. User confirmation remains pending.
