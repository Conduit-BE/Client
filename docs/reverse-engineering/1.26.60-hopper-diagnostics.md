# Hopper startup diagnostics, Linux

Tested 2026-11-05 on Linux x86-64 against the BedrockOnLinux 1.26.60.5 executable identified in [the investigation note](1.26.60-json-ui.md). No game process was attached to, injected into, or executed. Conduit implementation and configuration were unchanged.

## Observations

- The previous `/tmp/conduit-ui-search.json` contains a 600,000 ms `provider_timeout`. Its launcher stderr only records plugin discovery. It does not establish a license failure or a crashed bridge.
- The installed REA npm package is 6.7.0. The explicit launcher `/opt/hopper/bin/Hopper` has SHA-256 `b2271008fb82bf14cfae5c3644cdde2b11fc6804bd7c99d67032ec1b1942d53c`.
- A newly compiled tiny owned ELF containing `conduit_hopper_probe` returned that literal at `0x2004` successfully. REA Evidence: `ev_94f7c869755b183842ad3e2ee63b91c220c2944c4eeaa5a312d8299a06b4464a`.
- A MinGW-built x64 PE from the same source also returned the literal successfully at `0x140004050`. REA Evidence: `ev_d9cb95052729c8b7308b943b25bd964bec0c5a178499357f2dc3b6cb858a7708`. Its derived loader arguments were `-l WinPE --intel-64`.
- A Minecraft test used a **60-second startup deadline**, with intermediate process sampling and two private-display screenshots. At approximately 13 and 29 seconds the GUI showed `Loading Windows PE file...`, an indeterminate progress bar, and no registration or loader-choice dialog. The document still had unknown path/loader and no labels. This is a loader progress window, not the post-import background-analysis view.
- The real-target CLI ended at its 60,000 ms deadline with `provider_timeout`, `provider_state: not_started`, no search results, and only plugin-discovery stderr. The owned Hopper/Xvfb processes were cleaned up afterward.
- At 5, 13 and 48 seconds Hopper consumed approximately 112%, 129% and 137% CPU and 7,622,712, 7,680,068 and 7,933,516 KiB RSS respectively. At 29 seconds it was running with 14 threads and approximately 8.9 GB virtual memory. These measurements show active work and increasing memory, rather than an idle modal registration prompt. They do not reveal the responsible loader routine.

## Reproduce

The owned fixture and complete CLI results are local, ignored artifacts in `.local/hopper-diagnostics/`. The fixture source calls `puts("conduit_hopper_probe")`; build with `cc -g -O0 probe.c -o probe` and `x86_64-w64-mingw32-gcc -O0 probe.c -o probe.exe`.

Use the existing entry point, without changing REA/client settings:

```sh
HOPPER_LAUNCHER_PATH=/opt/hopper/bin/Hopper \
REA_HOPPER_STARTUP_TIMEOUT_MS=45000 \
node /absolute/path/to/rea-agents/scripts/rea.mjs \
search /absolute/path/to/probe.exe conduit_hopper_probe --provider hopper --format json
```

The real-target command replaced the path with the existing BedrockOnLinux `content/Minecraft.Windows.exe`, searched `button.reload_ui_definitions`, and used `REA_HOPPER_STARTUP_TIMEOUT_MS=60000`. While it ran, `ps -C Hopper -C Xvfb -o pid,ppid,etime,pcpu,rss,args` exposed the owned private display and Xauthority path. `DISPLAY=<owned display> XAUTHORITY=<owned authority> import -window root <output.png>` captured only that Hopper display. These ephemeral values must be obtained fresh for each test. No user desktop was captured.

Local retained evidence: `probe-search.json`, `probe-pe-search.json`, `minecraft-search.json`, `minecraft-processes.txt`, `minecraft-startup.png`, and `minecraft-startup-later.png` in `.local/hopper-diagnostics/`.

## Interpretation and next step

High confidence: Hopper's REA bridge, verified Linux demo adapter and both ELF and WinPE loader paths work for small inputs on this host. A universal missing bridge, missing license activation, or unsupported PE loader is contradicted by the successful controls.

High confidence for the observed interval: the Minecraft startup deadline was spent inside PE loading, with substantial CPU and memory consumption. No blocking registration or loader-selection dialog was visible in either capture. Unknown: whether import eventually completes, whether the PE's size/metadata causes pathological loader behavior, or whether later analysis would then take much longer. The earlier ten-minute attempt lacks screenshots and cannot prove it remained in this same stage throughout.

Increasing the deadline again without further loader profiling is unjustified. Native Linux Ghidra headless import is the practical alternative; native Windows is not required to diagnose or replace this static-analysis step. Successful fixture startup does not establish Minecraft UI reload semantics.

## Native Linux Ghidra readiness control

A subsequent fixture test used the locally extracted Ghidra 12.1.4 distribution and existing OpenJDK 21. With `GHIDRA_INSTALL_DIR=$PWD/.local/tools/ghidra_12.1.4_PUBLIC`, `XDG_CONFIG_HOME` scoped to `.local/hopper-diagnostics/ghidra-config`, and `XDG_CACHE_HOME` scoped to `.local/hopper-diagnostics/ghidra-cache`, the same REA CLI `search` command with `--provider ghidra` successfully imported and analyzed the owned x64 `probe.exe`. It returned `conduit_hopper_probe` at `0x140004050`, matching Hopper. The process exited successfully within a 120-second outer deadline (roughly 30 seconds), with no stderr. REA Evidence: `ev_05cc102101d7528dc197bdacf80e70bbbb722deb443a366af4d3d9843b0f7da3`; complete result `.local/hopper-diagnostics/ghidra-pe-search.json`.

This confirms the native Linux headless Ghidra integration works, including PE import, default analysis, bridge readiness and string search. No client registration was changed. This fixture control does not establish feasible default whole-program analysis time for Minecraft's much larger executable; the separate targeted static investigation controls that cost.
