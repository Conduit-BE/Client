# Frontend legacy screen diagnostics

Target: Bedrock Windows GDK x64 **1.26.60.5**, package **1.26.6005.0**,
2026-11-07. Original executable SHA256
`1d6ad5c217e9305442c353ba3e9bca623d5719134e1cc8a84fb1233f7145e85c`;
the existing standalone backend verifies the entire image. RVAs are exclusive
to that image. This supersedes the title-menu limitation in
[the original screen investigation](1.26.60-native-screen.md).

## Problem and reuse

The overlay rendered on the title screen, but name/control/binding/factory
metrics expired. The original observer accepted only the player-stack name
request at return RVA `0x65b0119`. Existing bounded observations already showed
`start_screen` rendering, alongside debug/toast screens. Those render observations
could not select the active menu safely and were deliberately not used as a
last-rendered fallback. Reload dispatch and FPS use independent paths.

Reused the matching Ghidra database, existing stack/name findings and owned
control traversal. Focused original PE unwind intervals were decompiled with
`ConduitUiProbe.java`; no whole-program analysis. Temporary Frida probes observed
natural stack accessors for 20 seconds and a separate 45-second transition
window. They did not call native functions, change game objects, scan heaps, or
reload resources. Local raw excerpts/events remain ignored under
`.local/re-investigation/menu-screen-20261107/`.

## Confirmed selection path

| RVA / method | Static evidence |
| --- | --- |
| `0x5675f0` | Existing SceneStack top accessor, vtable slots +0x188/+0x190. Windows x64 `(stack RCX) -> scene RAX`. Compares vector begin/end at +0x18/+0x20 and returns `[end-0x18]`, or null. Original first bytes `48 8b 41 20 48 39 41 18`. |
| `0x56cb30` | SceneStack slot +0x128: `48 8b 41 18 48 3b 41 20 0f 94 c0 c3`; returns whether the stack is empty. |
| `0x65b38d0–0x65b3b14` | Client selector obtains the player stack through virtual +0x738 and tests its +0x128 emptiness method. If empty, obtains the owner's frontend/global stack through virtual +0x3c8 and calls top slot +0x190. If nonempty, obtains the player stack and calls +0x188 instead. Both guarded views are released only after the top call returns. |
| return `0x65b39f7` | Top accessor call from the selector's **empty-player / frontend branch**. This is the only new production accepted caller. |
| return `0x65b3a42` | Same selector's nonempty-player branch. Existing player name observation remains responsible for gameplay. |
| `0x65b4ab0–0x65b4bc1`, return `0x65b4b09` | Another global top query. Deliberately not accepted: it can select background global layers in gameplay. |
| `0x53fb910–0x53fbc7d` | Renders a copied list of 16-byte scene/layer records. This confirms render ordering is not a substitute for selecting the engine's active stack. Not used for diagnostics. |

The temporary observation on native UI thread 280 recorded `start_screen`, legacy
scene table `0xf20ec60`, depth 4, from frontend caller `0x65b39f7`. Other global
queries independently returned the same title scene. Opening Play through normal
input changed this selector to a depth-5 scene with table `0xf220000`, the known
HBUI scene class. Thus Play on this build must not be traversed as legacy controls.
The probes detached normally and cleaned owned helpers; no crash was reported.

## Periodic source and integration

The selector's frontend call is event-driven, not a reliable periodic sampling
boundary: an initial implementation produced a valid title sample but it expired
again after one second. Follow-up static analysis established the precise getter
member chains used by that selector:

- Client vtable +0x738 → `0x65b4090`: player stack is `[client+0x5e8]`.
- Owner vtable +0x3c8 → `0x893930`: frontend stack is `[owner+0x1df8]`.
- Each getter returns a guarded view with that stack at result+0x10. Its guard
  token comes from stack+8 and shared ownership metadata from stack+0x10.

A separate 20-second passive observation compared these members against the
naturally returned getter views on UI thread 280: both matched exactly, both had
SceneStack table `0xf0829b0`; player depth was 0, frontend depth was 4. No getter
was called by the observer. This confirms the chains without a memory scan.

The final implementation adds **no hook**. The existing verified owner/UI-frame
callback calls `sampleFrontend` after its original frame returns and outside the
reload mutex. It checks the existing thread gate and exact owner, then at most
4 Hz reacquires the single primary client through the already-validated owner
map. Both stack pointers are read fresh from the verified members. It follows
the native selector's proven rule: only an empty player stack permits frontend
sampling. A nonempty player stack leaves the existing native name path unchanged,
so global toast/debug layers cannot replace gameplay diagnostics. Getter vtable
slots and concrete stack/scene/tree tables are checked against the exact image.

Only supported legacy scene/tree types are inspected. The frontend label is the
copied **runtime root-control identifier**, not a JSON definition or window-title
guess. The prior natural name experiment independently showed `start_screen` as
both root and native-produced name. Other roots are not promoted to
namespace-qualified JSON definitions or assumed to include controller suffixes.

Both producers share a 250 ms sampling gate and the same copied-name/count cache.
An empty-player callback explicitly yields before consuming that gate or
invalidating a snapshot. Without that handoff, empty player-name observations
can starve the frontend producer or clear its fresh results. The portable
`ScreenSampleGate` regression test covers repeated empty-player events followed
by successful menu refreshes beyond the one-second expiry interval.
The existing active-stack collector obtains Elements, Bindings and factory
statistics with unchanged traversal/counting semantics and budgets. No second
hierarchy walker, frame-order guess, name whitelist, native accessor invocation,
retained stack/scene pointer, or render-thread inspection is introduced. A scene
change selects new counts; unsupported/null frontend scenes invalidate the whole
snapshot instead of retaining previous world/menu totals. All stack/control
access stays inside the natural UI-frame callback and uses guarded memory reads.

## Limitations

HBUI Play/Settings are not legacy JSON UI trees: their DOM elements/bindings
are outside these counters. Static getter `0x4fd5ca0` confirms HBUI names come
from another service at scene+0x48 via a virtual borrowed-string-view method;
its provider layout has not been established here. No unverified call or fake
legacy total is substituted. Pure HBUI also may not execute the legacy native
font path used by F3 rendering. These remain separate limitations, not reasons
to count the title/background scene underneath an HBUI modal.

Split-screen remains unsupported by the existing single-client thread gate.
Synthetic snapshot tests cover coherent HUD → title → unavailable HBUI → HUD
replacement; they do not validate native offsets or scene selection. In-game
verification must confirm title values, return-to-title freshness, world/pause
behavior, Ctrl+R, stability and overhead. No release, tag or push is authorized.

## Standalone title verification

With no Frida attached, the final standalone sampler reported `start_screen`,
701 controls, 199 binding records, 6 factory instances, and 1 generated root
containing 3 controls. A viewport capture taken more than 25 seconds after the
first sample showed the populated fields and per-factory rows, with no expiry to
Unavailable. These are observations, not expected constants. The initial combined
collection sample was 1,092 µs; it is not a benchmark. Native title-menu Ctrl+R
also completed during development (UI callback and completion on thread 280).

All 8 portable and all 19 Windows/Wine checks passed during this change; after
the final handoff fix, the affected screen-metrics, targeted-standalone and
Ctrl+R tests were rerun and passed. Build SHA256:
`bcb57ea16bc992020adb78a3fef98a51067be170830de61e938c7ccaa47a50a0`.
