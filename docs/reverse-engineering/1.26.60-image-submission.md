## Question and reproduction

Can the existing UI renderer accept an embedded PNG safely, and can a single
title image use it without affecting pause/loading/HUD? Used the existing REA
investigation's verified UI-render-context vtable and a targeted Ghidra 12.1.4
headless fallback. No game process was executed, attached, or modified.

The original `.pdata` intervals were selected with
`tools/reverse-engineering/prepare_pe_ui_analysis.py`; the derived image clears
only the exception-directory descriptor, never instruction bytes. Import with
`-noanalysis`, then run `ConduitUiProbe.java` on RVAs `0x6c0d000`, `0x6c0d740`,
`0x6c0de80`, `0x6c11870`, `0x6c11a60`, and `0x6c11b60`. Reproduction instructions
for the exact toolchain are in `tools/reverse-engineering/README.md`. Private
outputs are ignored under `.local/re-investigation/title-logo-20261109/`:
`image-abi.manifest.json`, `image-abi.functions.tsv`, and `image-abi.txt`.
A second pass (`image-abi2.tsv` / `image-abi2.txt`) inspects nearby candidate
context methods; those investigated methods did not establish a texture loader.

## Observations

- Context vtable RVA `0xf2d18c0`, slot `+0x40`, points to RVA `0x6c0d000`.
  Assembly consumes context RCX, a pointer-sized image reference RDX, position
  float2 R8, size float2 R9, and stack UV-origin float2, UV-extent float2, and a
  flag byte. The function rounds position/size through the existing GuiData
  scale and appends a record; it does not decode PNG or create textures.
- The context's `+0x98/+0xa0/+0xa8` fields hold record begin/end/capacity.
  Each record is `0x30` bytes: borrowed reference at `+0`, position at `+8`, size
  at `+0x10`, UV origin at `+0x18`, UV extent at `+0x20`, flag at `+0x28`.
  Growth copies the pointer unchanged. No resource-reference increment happens
  during this submission.
- Slot `+0x48` points to RVA `0x6c0d740`, which constructs records from a larger
  image description and additional image segments. It also retains the supplied
  image reference address unchanged.
- Slot `+0x50` points to RVA `0x6c0de80`. Its normal path iterates these records,
  emits vertices through RVA `0x541a6f0`, and submits the referenced texture via
  RVA `0x5ad6a80` or `0x5ad6900`. The alternate path copies a two-qword
  refcounted resource representation from the borrowed address. The object is
  not proven to be a raw D3D shader-resource pointer.
- The executable contains RTTI lambda names mentioning
  `SpriteComponent::_drawClipped`, `_drawTiledClipped`, and `_drawTiled`, with
  `UIRenderContext` and `ImageInfo` arguments. This corroborates legacy image
  composition but does not identify the live title SpriteComponent.

## Interpretation, impact, and unresolved requirements

Confidence is high for the static deferred-record layout and **borrowed** image
reference lifetime. The image-submit ABI is a candidate based on instructions;
no natural-call runtime observation or custom image draw validates it yet.

A temporary stack texture wrapper cannot safely be substituted just for the
submit callback: image flush can occur later, after that wrapper is destroyed.
Likewise, the supplied PNG byte span cannot be passed as an image handle. These
would be unsafe implementations even though their signatures compile.

This work does not establish a PNG decoder/import contract, texture creation,
resource origin, a title-specific SpriteComponent identity, or resource teardown.
It does not justify enabling `mainMenuLogo`, adding native addresses to a
supported profile, or installing a global texture replacement. Client source is
unchanged by this investigation.

A safe follow-up needs natural title draw observations tied to the independently
verified active legacy frontend view and default control ancestry. Trace its
borrowed image reference back to creation/ownership, establish a supported
embedded-byte upload or private-cache resource load and its exact destruction
contract, then preserve ownership through all deferred flushes and shutdown.
Validate actual pixels, title/pause/loading/HUD/custom-title isolation, GUI
scaling, device recreation, Ctrl+R and Ctrl+K before declaring the feature working.

## Follow-up: resource lookup and native constructor

The initial loader search above was subsequently extended. The primary context
vtable slot `+0x100` is RVA `0x6c0e600`:
`(context, out32, ResourceLocation*, bool) -> out32`. Static instructions show
that it forwards ordinary locations to RVA `0x541f580` using the context's
borrowed texture group. Location type 10 chooses another texture group.
The 32-byte result contains two native shared ownership pairs; it is not a
single raw image pointer. The image pointer from the first pair is the one
stored by SpriteComponent and passed to deferred drawing. These declarations
remain inferred from exact-build assembly until observed during native calls.

SpriteComponent render RVA `0x1c46c10` uses an inline 56-byte ResourceLocation at
`+0x20`. On a cache miss, at return RVA `0x1c46d8a`, it calls the above getter,
then moves the first ownership pair into `+0x118/+0x120` and the second into
`+0x128/+0x130`, releasing displaced references via native virtual destructors.
Helper `0x1c4a550` uses the image pointer in `+0x118`, preserves its aspect
ratio, applies the UV scale at `+0x1d0`, and invokes image submission. The root
worker separately owns the live-validation evidence; these are static results.

The exact image's string-span table at RVA `0xeffd550` names filesystem values:
0 `InUserPackage`, 1 `InAppPackage`, 2 `RawPath`, 3 `RawPersistent`,
4 `InSettingDir`, 5 `InExternalDir`, 6 `InServerPackage`, 7 `InDataDir`,
8 `InUserDir`, 9 `InWorldDir`, 10 `StoreCache`, 11 `MaterialsDir`.
Each entry is a 16-byte `{pointer,length}` span. Instructions at
`0x8c5ef7..0x8c5f0a` multiply the selected enum by 16 and index that table,
corroborating the ordinal mapping. This mapping alone does not prove a
particular file exists, decodes successfully, or is accepted by the loader.

Native ResourceLocation constructor RVA `0x3946b0` is called from the
SpriteComponent constructor `0x1c465d0` at `0x1c46632`, with
`RCX=component+0x20` and `RDX=&{const char*,size_t}`. It constructs filesystem
value zero, copies the span through the game's allocator, and writes string
length/capacity at `+0x18/+0x20`. The constructor stores the path hash at
`+0x28`. Instructions `0x394874..0x394885` compute the combined hash at `+0x30`:

```text
combinedHash = ((uint8(filesystem) XOR 0xcbf29ce484222325)
                * 0x100000001b3) XOR pathHash
```

All arithmetic is modulo 2^64. The observed path hash multiplies then XORs each
byte, starting from `0xcbf29ce484222325`; an empty/null path has hash zero.
Consequently a separately owned constructor result can select the observed
RawPath value by changing its type and recomputing the combined hash from the
constructor's own path hash. This does not mutate a shared vanilla location.
The constructor allocates the string; a consumer must establish destruction or
retain ownership, never free it through the client's unrelated allocator.

Private focused output: `image-texture.txt`, `image-origin.txt`,
`image-component.txt`, and their TSV interval lists. The temporary reusable
Ghidra project is `/tmp/conduit-logo-ghidra/Logo.gpr`, program `image-abi.exe`.

### Resource destruction and safe validation sequence

RVA `0x17e9a0` destroys the 32-byte two-pair image lookup result. Its assembly
reads the second pair's control block at `+0x18`, decrements strong ownership at
control `+8`, calls virtual slot zero when it reaches zero, then decrements weak
ownership at control `+0xc`, calling slot one at zero. It repeats that sequence
for the first pair's control block at `+8`. It does not clear the caller's
storage. The native image flush calls this same helper for this representation.
Consumers must call it at most once per owned result and clear their copy.

The ResourceLocation string destructor is inlined in SpriteComponent's deleting
destructor RVA `0x1caa720`, instructions `0x1caa87d..0x1caa8c8`. With string
capacity `+0x20` below 16, no heap release occurs. For a capacity of at least 16
and allocation size below 4096, it calls native deallocator RVA `0xe934b00`
with the pointer at `+8` and size `capacity+1`. Larger strings use a separate
aligned-allocation branch. A consumer that restricts its generated PNG path to
less than 1024 bytes and verifies the constructor's resulting capacity remains
below 4095 can use that proven smaller branch. Do not use the client's CRT
allocator for native-owned string memory. The destructor resets length zero,
capacity 15, and the first inline byte zero. No standalone ResourceLocation
cleanup method was identified here.

A bounded runtime proof should first create a separately owned location and
invoke native lookup during a naturally observed legacy UI render callback.
Keep its output alive without replacing any game pointers. Require that the
lookup resolves and reports PNG dimensions 2004×686. Only then substitute the
separately owned image reference for the exact default title image submission,
preserving splash/layout and aspect ratio. The original image/control/scene
must remain owned by Minecraft. Retain the replacement through all native
image flushes; release only at a known UI-thread queue-empty boundary after
replacement submission has stopped. Callback count zero alone does not prove
that a previously queued borrowed image reference has been flushed.

The title root name, control ancestry, vanilla source location, and known image
dimensions together narrow scope but do not alone establish vanilla resource
provenance: a custom pack can preserve those values. A production guard must
also reject customized title definitions/resources through a supported resource
origin or active-pack validation mechanism. This static investigation does not
claim that guard established.
