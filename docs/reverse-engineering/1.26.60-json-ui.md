# Bedrock 1.26.60 JSON UI investigation

Checked 2026-11-05, Linux x64 analysis host, Windows x64 GDK client under BedrockOnLinux/Proton. This note supersedes the old package-format blocker for this installation; it does not supersede the unverified reload interfaces in the 1.26.52 note.

**Follow-up:** Linux static analysis recovered concrete legacy references and a reload-button callback chain. See [the legacy-only findings and stopping point](1.26.60-legacy-reload-path.md) and [Hopper diagnostics](1.26.60-hopper-diagnostics.md). These supersede the earlier statement below that no function entries had been identified. The complete callable reload contract remains unverified. Newer UI systems are outside further investigation scope.

## Identity and question

The host process list identified Linux PID 130911 (`MINECRAFT MAIN`) with command line `X:\.local\share\bedrock-on-linux\content\Minecraft.Windows.exe`. The launcher's `settings.json` selected `1.26.60.5`. Its `content` path resolves to `games/release/1.26.60.5`; both `appxmanifest.xml` and `MicrosoftGame.Config` identify package version `1.26.6005.0`, x64. This identifies the launched installation; no in-process version API was queried.

REA `open_binary` accepted this executable as PE x86-64, SHA-256 `1d6ad5c217e9305442c353ba3e9bca623d5719134e1cc8a84fb1233f7145e85c`. Unlike the older local `1.26.5203.0` artifact, this copy is analysis-ready without transforming its bytes.

Question: which native interface reloads legacy JSON UI, how is its owning object obtained, which thread owns the operation, and can failures preserve the previous working screen?

## Observations and reproducible probes

1. REA `list_frida_processes` with `device_id: local` independently enumerated PID 130911 and its game command line.
2. REA `inspect_with_objdump`, `operation: section_headers`, returned `.text` at analysis VMA `0x140001000`, file offset `0x400`; `.rdata` at VMA `0x14eec7000`, file offset `0x0eec5e00`; and `.pdata` at VMA `0x152bdd000`, file offset `0x12873600`. Evidence ID: `ev_36e3de02e917c47348d4b8a5733831139cc6f507a1048ada500168f6a5fb486d`. These are static loader coordinates, not observed runtime addresses.
3. Repeat literal discovery with `strings -t x <executable>` and search for `button.reload_ui_definitions`, `ui/_ui_defs.json`, and `ClientboundDataDrivenUIReloadPacket`. GNU strings reported the first two at file offsets `0x0f54c106` and `0x0f581347`. These offsets belong only to the SHA-256 above. String existence does not establish a function, a reachable button, or reload semantics. The packet name may refer to a separate data-driven UI subsystem.
4. REA `search_strings` using regex `reload.*ui|ui.*reload|_ui_defs` failed before query execution because Hopper exceeded its 120-second startup deadline. `binary_session` confirmed the Hopper binding and reported no configured Ghidra installation. A separate offline CLI run with `REA_HOPPER_STARTUP_TIMEOUT_MS=600000` also failed with `provider_timeout` waiting for bridge readiness. It returned no search results or analysis snapshot; the timeout cannot distinguish unfinished analysis from a pending loader/demo/license dialog. Its JSON diagnostic is retained locally at `/tmp/conduit-ui-search.json`. No client or REA configuration was changed.
5. A single REA `instrument_with_frida` attach requested only architecture and module enumeration, filtering Minecraft, Conduit, D3D12 and DXGI. It failed with `Process with pid 130911 either refused to load frida-agent, or terminated during injection`. A subsequent host `ps -p 130911` found no process. The attach attempt may have caused the exit; there is no crash diagnosis establishing causation. No module inventory, target call stack, function execution, or live UI state was recovered. Do not repeat this attach as a validation step.

## Interpretation and confidence

High confidence: this is the requested release installation, and its disk executable can be inspected as a PE. High confidence: the listed literals exist in that executable. Low confidence: the button literal leads to a usable legacy UI reload operation. Unknown: concrete function entries, instance acquisition, vtable slots, ABI, reload ordering, thread affinity, and failure/rollback behavior. No game offsets or guessed calls are suitable for client code yet.

## Client impact and validation

`src/core/json_ui.*` validates the watched disk tree and publishes metadata atomically. `src/client.cpp` skips backend invocation on parsing/read failures. `src/platform/windows/auto_start.cpp` publishes synchronized F3 diagnostics through `NotificationCenter`; the D3D12 renderer draws them on its existing presentation path. The panels explicitly identify the reload backend as unsupported. They do not inspect live UI controls, mount the development directory, or assert successful Minecraft reloads.

Native core tests cover parse failure retention, namespace validation, deletion, recovery, and persistent diagnostics. Windows/Wine tests cover DLL lifecycle, loader contract, automatic initialization, synthetic F3 show/hide, Ctrl+R, renderer pixels, and presentation hooks. These harness results do not establish visibility or compatibility in the actual game. BedrockOnLinux was configured for another DLL with automatic injection disabled; its settings were left intact.

For game validation, select the built Conduit DLL in BedrockOnLinux's injector, launch the selected licensed release, confirm the Conduit log and F3 panels, edit a watched JSON file, then introduce malformed JSON and check the logged filename and retained metadata. This validates only diagnostics. Actual hot reload still requires offline recovery of the owning reload interface and a controlled test proving thread ownership and last-known-good behavior before implementing it.
