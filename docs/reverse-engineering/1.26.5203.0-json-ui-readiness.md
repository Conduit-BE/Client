# Minecraft 1.26.5203.0 JSON UI investigation

**Checked:** 2026-10-20. **Target identity:** `/proc/238258/cmdline` identified the live Wine process as `games/release/1.26.52.3/Minecraft.Windows.exe`. That installation's `appxmanifest.xml` and `MicrosoftGame.Config` identify `1.26.5203.0`, x64. Its executable SHA-256 is `4a321e71e10418056b1e2aa8f2634e60d20e92b7314ae07a58964c7bed4015c2`, identical to the Xodus copy. This verifies the launched package path and version metadata, though no in-process version API was queried. **Platform target:** Windows x64 under BedrockOnLinux/Proton; analysis host is Linux x64.

## Findings

- Microsoft’s JSON UI reference distinguishes `_ui_defs.json` (the list of UI screen files), UI elements, global variables, and screen definitions ([Microsoft JSON UI reference](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/jsonuireference/examples/jsonuilist?view=minecraft-bedrock-stable)). Community documentation describes `RP/ui` file discovery, `ui_defs`, namespaces, control references, factories, and screen roots ([Bedrock Wiki: introduction](https://wiki.bedrock.dev/json-ui/json-ui-intro.html), [dynamic factories](https://wiki.bedrock.dev/json-ui/dynamic-content-generation.html)). These describe content semantics; neither documents native implementation functions or addresses.
- Mojang's 1.26.0 changelog explicitly includes JSON UI behavior changes and separately describes consolidated scaling across JSON UI and Ore UI. This confirms both UI paths are relevant in the 1.26 release line; it does not establish which screen types use which path in this exact package ([1.26.0 update notes](https://learn.microsoft.com/en-us/minecraft/creator/documents/update1.26.0?view=minecraft-bedrock-stable)).
- Mojang’s public [`bedrock-samples`](https://github.com/Mojang/bedrock-samples/tree/main/resource_pack) repository contains resource-pack examples, including UI JSON, but no Bedrock client parser/renderer source. In the inspected local package tree, `vanilla/contents.json` indexes UI textures, while no plain `ui/*.json` screen definitions were found. `vanilla/__brarchive/ui` contains four opaque `.brarchive` entries; these were not decoded. `data/resource_packs/oreui` and `data/gui/dist/hbui` are present, so this package also ships a separate Ore UI/web UI asset tree. The coexistence or replacement relationship with legacy JSON UI is not established by these observations.
- Open-source LeviLamina generated API headers expose concrete declarations for [`IUIDefRepository`/`UIDefRepository`](https://docs.levimc.org/LeviLamina/api/da/d72/src-client_2mc_2client_2gui_2interface_2IUIDefRepository_8h_source.html), [`UIResolvedDef`](https://docs.levimc.org/LeviLamina/api/d4/d6a/src-client_2mc_2client_2gui_2UIResolvedDef_8h_source.html), [`UIControlFactory`](https://docs.levimc.org/LeviLamina/api/d1/d46/src-client_2mc_2client_2gui_2controls_2UIControlFactory_8h_source.html), [`ISceneFactoryImpl`](https://docs.levimc.org/LeviLamina/api/d5/d76/src-client_2mc_2client_2gui_2screens_2ISceneFactoryImpl_8h_source.html), [`SceneFactory`](https://docs.levimc.org/LeviLamina/api/dd/daf/src-client_2mc_2client_2gui_2screens_2SceneFactory_8h_source.html), [`IMinecraftGame`](https://docs.levimc.org/LeviLamina/api/dd/d04/classIMinecraftGame.html), and [`IUIRepository`](https://docs.levimc.org/LeviLamina/api/d6/d8b/src-client_2mc_2client_2gui_2interface_2IUIRepository_8h_source.html). The headers also declare `IMinecraftGame::handleReloadUIDefinitions()` and `recalculateScene()`. These names exist in that project's reverse-engineered API for a different, non-matching supported build, not in the protected `1.26.5203.0` executable. LeviLamina currently documents client support for `26.51.1`, which is not evidence for this target ([supported versions](https://docs.levimc.org/LeviLamina/versions/)).

## Analysis environment and blockers

- REA `binary_session` (`rea-agents` 6.7.0) reports its Hopper provider available at `/opt/hopper/bin/Hopper`; the provider version was not reported by REA. Ghidra is unavailable in this host: no configured installation and no Java runtime.
- The installed `Minecraft.Windows.exe` is 311,218,176 bytes and byte-identical to the Xodus copy, SHA-256 `4a321e71e10418056b1e2aa8f2634e60d20e92b7314ae07a58964c7bed4015c2`. `file` identifies it only as `data`; REA `open_binary` with Hopper rejected it as `target_unavailable` / `unsupported binary format`. No matching PDB, Hopper database, IDA database, or map/symbol file was found in the local target tree. A literal string search for the six priority method names in this on-disk executable found no match. No protection removal, entitlement bypass, or binary patching was attempted.
- A targeted public search did not locate a legitimate PDB or compatible analysis database for this exact game build. Microsoft documents its public symbol server as a source of symbol files, but this target provides no usable PE/CodeView identity to request a matching PDB; Microsoft GDK packaging guidance also lists PDBs among files to remove from shipping content ([symbol server](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/using-a-symbol-server), [GDK packaging](https://learn.microsoft.com/en-us/gaming/gdk/docs/features/common/packaging/overviews/packaging-getting-started-for-pc?view=gdk-2510)). This is not proof that no privately or separately published symbols exist.
- The sandboxed process list hid the host process. A read-only host process listing found live Linux PID `238258` (Wine process name `MINECRAFT MAIN`), launched through the installed `1.26.52.3` package. `/proc/238258/maps` showed probable main-image base `0x140000000`: its first page was backed by a deleted BedrockOnLinux shared-memory object, executable pages `0x140001000–0x14e5a7000` were anonymous, and no file-backed `Minecraft.Windows.exe` mapping was listed. These are **absolute runtime mapping addresses**, not RVAs or function entries. The main-image attribution follows the command line and expected PE layout; it has not been confirmed through a module-list API. The same maps list `RenoirCore.WindowsDesktop.dll` at `0x6ffffcf20000` and `cohtml.WindowsDesktop.dll` at `0x6ffffe910000`; neither is thereby identified as JSON UI code.
- Frida `17.23.2`'s native binding was initially missing. Its official matching Linux x64 prebuilt binary was installed with the package's `scripts/install.js` after placing its bundled `prebuild-install` executable on `PATH`. A fresh Node process successfully enumerated Frida devices and found PID `238258`. The already-running REA MCP worker still returns its cached missing-binding failure and needs restarting before REA Frida tools can be used. Frida enumeration was read-only; no attach or instrumentation occurred. The host has GNU gdb 18.1 and WineDbg; no `strace`, `ltrace`, `perf`, or `bpftrace` executable was found. The current sandbox has `ptrace_scope=1`, no effective capabilities, and seccomp, so direct GDB attach from its namespace has not been established.
- WineDbg with the matching Proton Wine prefix listed the game as Windows PID `0x20` (63 threads). A short script requested `attach 0x20`, `info share`, `detach`, and `quit`, with no breakpoints or writes. WineDbg printed `attached`, then `Exception c0000005` and `Internal crash at 0000000000479885` while reporting `0 modules`; the game Linux PID was gone immediately afterward. The trace did **not** establish whether the debugger fault itself caused the game exit, but attach is unsafe to repeat without a recovery plan. No WineDbg module list, stack, or function instruction address was recovered from it.

## Highest-value next experiment

On one future licensed launch, enable Wine's file-access diagnostic channel from startup and make one controlled transition into a known legacy JSON UI screen, capturing only the relevant `ui/` and UI texture paths/timestamps. This avoids the WineDbg attach path that failed and tests whether the transition reads UI content on demand; a no-read result would suggest caching or another load point, not absence of JSON UI. To turn any subsequent call-stack instruction address into a verified function RVA, first obtain a reliable, non-mutating debugger/sampler for this Proton process or a legitimate analysis-ready artifact, confirm the main module base, and independently establish the function boundary. Frida's binding is repaired, but its normal attach/instrumentation path is outside the current no-memory-modification constraint. No internal reload candidate should be invoked.
