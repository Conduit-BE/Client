# Debug overlay: bounded native evidence review

Date: 2026-11-06. Target: Bedrock Windows GDK x64 1.26.60.5, package 1.26.6005.0. Identity comes from the existing exact-image validation in `src/experimental/legacy_reload.cpp` and the [confirmed reload investigation](1.26.60-json-ui-only-prototype.md); no new game session or live screen trace was performed during this implementation.

Question: can the established reload context safely identify the active legacy screen and enumerate its runtime controls? Secondary question: is an engine FPS metric already established?

Method: reuse prior Ghidra 12.1.4 output and versioned notes rather than run another whole-image analysis. Review the targeted callback/action/context findings and saved excerpts for original-image RVAs `0x8c1e80`, `0x8c41f0`, `0x8c44c0`, `0xde790`, `0x1872e40` and `0x6583170`. The machine-local preserved excerpts are under `.local/re-investigation/legacy-ui-only-20261106/`; reproducible project preparation/function selection is in [the tooling guide](../../tools/reverse-engineering/README.md) and [the targeted reload note](1.26.60-json-ui-only-prototype.md). Search terms in versioned notes: `screen`, `ScreenView`, `ScreenStack`, `FPS`; inspect loader/category invalidation code, not just names. REA session status was checked: no active native target; the saved evidence was reused. No new native tool evidence ID is claimed.

Observations:

- Existing callback RVA `0xf203e0` and action `0x6583170` establish the complete reload action, including a category task barrier and collection invalidation. The associated validated UI context is documented for this purpose only.
- Saved `0xde790` pseudocode calls `0x1872e40` with category arguments including `0xf` and `0x10`; the latter traverses a keyed collection. Neither excerpt establishes that this collection represents the displayed screen or its controls.
- The reviewed evidence has no established accessor for topmost/focused screen, legacy namespace/name mapping, runtime child enumeration, object lifetime ownership for such enumeration, or native FPS value.
- Prior D3D12 HUD tests prove an isolated rendering path under Wine; the existing HUD status explicitly leaves Minecraft visibility unconfirmed. Its queue-by-device heuristic does not establish the game's presentation queue when several direct queues exist.

Interpretation: inferring active screen identity or element count from these reload collections would be unjustified. Confidence is high that the *reviewed evidence is insufficient*, not that Minecraft lacks such facilities. Screen-stack/controller/view and engine-FPS existence remain unresolved. No offsets from this review are added to executable overlay code.

Code impact: `src/platform/windows/debug_overlay.cpp` displays `Unavailable` for Screen and Elements, performs no native UI reads, and measures successful public DXGI presentation cadence as explicitly labeled. `src/core/presentation_rate.hpp` handles a bounded rolling mean. Native screen access therefore cannot introduce stale pointers, recursive traversal, or cross-thread UI reads in this implementation.

Next bounded experiment, after the first manual overlay checkpoint: locate a candidate active-screen accessor in the exact image, establish its call site on a naturally executing UI thread, and compare emitted identifiers across one known legacy menu transition and one modal stack transition. Establish whether names denote native scenes or JSON roots before displaying them. Only then inspect root ownership and child storage, define root inclusion, and impose visited-node and node/time limits for a periodic snapshot on the owning thread. No child pointer is to be retained for the overlay worker.

Validation: follow [the overlay checkpoint](../debug-overlay.md). Current screen selection, root inclusion and element-count refresh policy remain undefined because the native mechanism remains unverified; the shipped field is explicitly unavailable.
