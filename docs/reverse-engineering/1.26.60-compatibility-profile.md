# Compatibility profile migration — Bedrock 1.26.60.5

2026-11-08, Windows GDK x64, Bedrock 1.26.60.5, package 1.26.6005.0.
This is a source migration of previously verified findings, not a new live-game validation.
The executable identity remains SHA-256
`1d6ad5c217e9305442c353ba3e9bca623d5719134e1cc8a84fb1233f7145e85c`.

Question: can native reload and F3 rendering select a verified per-build contract
instead of embedding addresses throughout their implementations?
Method: compare the existing loader, frame, completion, screen-name and renderer
hook guards, vtables and structure accesses against the versioned findings:
[reload](1.26.60-legacy-reload-path.md), [targeted UI action](1.26.60-json-ui-only-prototype.md),
[screen](1.26.60-native-screen.md), [controls](1.26.60-ui-controls.md),
[factories](1.26.60-ui-factories.md), [bindings](1.26.60-ui-bindings.md),
[frontend](1.26.60-menu-screen.md), [rendering](1.26.60-native-debug-rendering.md).

Observation: these paths share the same exact-image guard but had separate local
constants. All supported native RVAs, hook prefix bytes and named layout fields
now reside in `src/minecraft/versions/bedrock_1_26_60_5.hpp`.
The broad resource-reload dispatcher was removed; it is not an available profile
feature. Native text ABI declarations still reflect the sole verified build.

`detectRunningExecutable()` reads the executable file version when present,
hashes the complete file and reads its PE machine. `selectCompatibility()`
requires AMD64 and the exact known SHA. File version is diagnostic metadata;
a matching version string cannot authorize modified code. No other image is
supported, and a missing file version does not weaken the exact hash check.
The renderer requires prior successful profile selection and retains its entry
prefix guards. Feature flags independently gate targeted reload, screen sampling
and native rendering. Main-menu logo replacement is marked unsupported.

Confidence: high for the mechanical migration, based on preserving the prior
values and exact hash; runtime behavior still needs in-game verification.
The remaining risk is the same as before: the documented native ABI is private
and can change in any executable update. No signature search or nearest-version
fallback is attempted.

To add a version, first collect versioned RE evidence for that exact executable,
including the full hash, architecture, native signatures, layouts and callback
lifetime rules. Add a dedicated profile header; register its exact identity in
`selectCompatibility()`. Set unsupported feature flags false and do not populate
unverified addresses by copying another version. If an ABI differs, provide an
explicit version-specific adapter instead of assuming a new offset is enough.
Add selection/rejection tests and validate each enabled feature in that game.

Validation: portable compatibility tests reject changed hashes and architectures
and ensure pure profile selection cannot authorize runtime hooks. Cross-compile
both native callers. In-game checks: confirm initialization on the original
build, Ctrl+R targeted reload, F3 rendering, screen/control/factory/binding data,
and rejection of unsupported images before native address access.
