# Frida under BedrockOnLinux/Proton — working Linux workflow

Tested **2026-11-06**, Linux x64 host, Bedrock **1.26.60.5**, package **1.26.6005.0**, Windows x64 under BedrockOnLinux. **Windows `frida-server` plus a Linux remote client successfully inspected Minecraft's modules and detached. Native Windows and a VM were not needed.** No legacy UI internals were called or investigated in this pass.

## Research and previous failure

Read [Frida issue 3339 and its comments](https://github.com/frida/frida/issues/3339). The issue describes Linux-device injection into Wine crashing while trying to locate libc. The maintainer suggests a Windows Gadget; a later contributor reports working Windows `frida-server` inside Wine, accessed remotely from Linux. The [FREAT article](https://suidpit.sh/posts/freat-intro/#wine-support-and-steam-proton-too) explains that server approach, and its [Wine provider implementation at revision 9506a9027a0b533f2bd5054a23a518230d67bda7](https://github.com/suidpit/freat/blob/9506a9027a0b533f2bd5054a23a518230d67bda7/server-python/src/freat_server/targets/wine.py) downloads a server matching the client version, starts it with the selected Wine binary/prefix, and connects remotely. The article was accessible with a standard browser user agent after the initial requests failed.

The earlier Minecraft attempt selected Frida's **Linux local device**, using Linux PID 130911. Its error did not include an agent-side backtrace or the issue's libc diagnostic. Therefore the exact cause of that crash is **not established**. A mismatched native Linux injection route into a Wine-hosted Windows process is the supported explanation, not a proven crash diagnosis. It was not repeated. The successful replacement uses Windows process IDs and a Windows agent through the remote Windows server.

## Controlled results

1. **Disposable isolated prefix, same Wine engine:** compiled `ConduitFridaProbe.exe` with MinGW x64, started it and the Windows server in a fresh `.local` prefix. Remote enumeration and one attach succeeded. Agent reported `windows` / `x64`, enumerated **29 modules**, read the probe's `MZ` header and exported marker `0x434f4e44`, and detached normally. The probe remained alive. That prefix's owned wineserver was stopped afterward.
2. **Active game prefix, helpers outside the runtime namespaces:** enumeration worked and found Minecraft, but the disposable probe attach failed with `WriteProcessMemory returned 0x00000005`. Its console confirmed it had started. **Minecraft was not attached.** Owned helpers were stopped; the game remained running.
3. **Same active prefix, helpers launched inside the game's namespaces:** a no-op `nsenter` check succeeded. The server and probe were launched using `nsenter --target <game Linux PID> --user --mount --preserve-credentials`, the same Wine binary, and the running game's selected Wine/runtime environment. Probe attachment, all 29 modules, header/marker reads and detachment succeeded.
4. **Minecraft, one attempt after step 3 passed:** remote server enumerated Windows PID **276**, corresponding to observed Linux PID **223064**. Agent reported `windows` / `x64` and enumerated **116 modules**. Main image was `Minecraft.Windows.exe`, base `0x140000000`, size `327397376`, path `X:\.local\share\bedrock-on-linux\content\Minecraft.Windows.exe`. DXGI and D3D12 modules were visible. Detachment was `application-requested`, with no reported crash. The process remained present both after detachment and after owned-helper cleanup. No second Minecraft attach was made.

The outside/inside comparison supports matching the runtime namespaces as part of the fix. Namespace inspection showed that Minecraft and its wineserver share a child user/mount namespace; the host helpers did not. The corrected launch also copied `LD_LIBRARY_PATH` and `WINEDLLPATH`, so the experiment does **not isolate namespace membership as the sole cause** of access denial. No kernel trace was taken. Neither Yama (`ptrace_scope=1`) nor other system security settings were changed.

## Reproduction

Own-source tools are in `tools/reverse-engineering/frida-proton/` (Python 3.11+ for the launcher):

- `probe.cpp`: disposable Windows x64 fixture; exported marker is for testing reads only.
- `inspect-remote.mjs`: Linux Node remote client; enumerates, attaches once, inspects, unloads and detaches. Only the probe has header/exported-marker reads; Minecraft's script enumerates process/module metadata only. No hooks, memory-write APIs or `NativeFunction` calls are used. Frida necessarily loads its own agent during attachment.
- `validate.py`: selects environment from a verified live Minecraft Linux PID, starts helpers in that process's user/mount namespaces, tests the probe first, and optionally inspects Minecraft. Default is **probe only**. Failures stop the workflow. It never kills the shared wineserver or signals Minecraft; only its owned server/probe subprocesses are stopped.

Download and verify the matching server before extracting it; keep the files under `.local/frida-proton/`. Build the fixture:

```sh
mkdir -p .local/frida-proton
x86_64-w64-mingw32-g++ -std=c++20 -O0 -static \
  tools/reverse-engineering/frida-proton/probe.cpp \
  -o .local/frida-proton/ConduitFridaProbe.exe
```

Set `CONDUIT_FRIDA_MODULE` to the installed **17.23.2** Node entrypoint, for example the existing REA package's `node_modules/frida/build/src/frida.js`. The original machine used `/home/zelisce/.npm/_npx/a1722018f28f9df2/node_modules/frida/build/src/frida.js`; discover the installed path afresh in another environment. No global REA edit is required.

Use a current **Linux** PID for `--game-linux-pid`; do not reuse PID 223064 from these observations. The script verifies the original game file hash and package version and derives the active Wine prefix/engine from `/proc/<pid>/environ`. Choose a fresh output directory so earlier evidence is preserved:

```sh
CONDUIT_FRIDA_MODULE=/absolute/path/to/frida/build/src/frida.js \
python tools/reverse-engineering/frida-proton/validate.py \
  --game-linux-pid CURRENT_LINUX_PID \
  --game-exe /absolute/path/to/bedrock-on-linux/content/Minecraft.Windows.exe \
  --server-exe "$PWD/.local/frida-proton/frida-server-17.23.2-windows-x86_64.exe" \
  --probe-exe "$PWD/.local/frida-proton/ConduitFridaProbe.exe" \
  --output-dir "$PWD/.local/frida-proton/run-01"
```

After the probe succeeds, an intentional subsequent run can add `--inspect-minecraft` and use another fresh output directory. That run again gates the one Minecraft attach on probe success. Runtime helpers listen on a dynamically selected **loopback-only** port. The remote endpoint uses Windows PIDs returned by that server, not Linux PIDs. Raw client use is `node inspect-remote.mjs HOST:PORT PROCESS_NAME OUTPUT.json` with the same Frida module environment variable.

The successful experiment used the equivalent local prototypes before parameterization; the portable scripts received Python/Node syntax checks. They were not used for an additional Minecraft attach. A host sandbox may require permission to read process environment, enter the owned namespaces and open loopback sockets. If `nsenter` is denied, stop rather than changing system policy or using an unverified context.

REA's existing Frida tools accept a `remote.address` such as `127.0.0.1:PORT`; this can use the server while it is intentionally running. That specific REA remote connection was **not** separately validated, because the Node remote client already established the requested result and no further attach was needed.
