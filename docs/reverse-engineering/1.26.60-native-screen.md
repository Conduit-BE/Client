## Observations

- The constructor at `0x562100` installs table `0xf0829b0`, initializes a vector at object offsets `+0x18/+0x20/+0x28`, and uses the literal `SceneStack UI destroy group`. This supports identifying the object as the concrete SceneStack implementation.
- Leaf `0x5675f0` loads the vector end at `+0x20`, compares it with begin at `+0x18`, and returns `[end-0x18]` or null. SceneStack vtable entries `+0x188/+0x190` point here. Related iteration increments entries by `0x20`; the scene is at entry `+8`.
- `0x567520` obtains `[end-0x18]` and invokes the supplied callback with that scene first. It then iterates entries descending using `+0x88` as a bound, skips that first scene, tests each other scene through virtual slot `+0x150`, and invokes the callback for qualifying scenes. This demonstrates simultaneous scene layers, rather than a single globally unique visible scene. A lambda signature names `SceneStack::forEachVisibleScreen`; the relationship supports this interpretation, but the exact meaning of slot `+0x150` is unresolved.
- `0x56d000`: Windows x64 RCX is the stack; RDX is caller-owned result storage. On a nonempty stack it obtains `[end-0x18]` and calls the scene's virtual `+0x1b8` with RDX preserved. Empty/null cases initialize an empty 32-byte MSVC-style string with capacity 15. The returned RAX is the result-storage pointer. No direct code displacement references were found by `find_rip`; virtual callers remain to be established at runtime.
- `0x56d050` has the same selection/result pattern but dispatches virtual slot `+0x1e8`. These two strings must not be assumed equivalent.
- `UIScene - render` points to `0x4ccf520`. Its function pointer occurs in table `0xf20ec60` at slot `+0x98`. This table's slot `+0x1b8` points to leaf thunk `0x4cd2860`, which loads `[scene+0x40]` and jumps to `0x4cc7530`. Slot `+0x1e8` points to `0x4cd2ca0`.
- `0x4cc7530` loads `[view+0x50]`, then a shared root/control pointer at that object's `+8` and its reference-count storage at `+0x10`. It obtains string bytes from root `+0x20`, size `+0x30`, capacity `+0x38`; capacity below 16 denotes inline storage. It also obtains a string from `[view+0x40]` through virtual slot `+0xd8`, then calls `0x11d1f0` with root and controller string temporaries. **The exact composition/meaning is not yet confirmed**; a root control name alone must not be labeled the native screen name or a namespace-qualified JSON definition.
- `0x4cd2ca0` also combines a controller-provided string with the root string, falling back to `0x4cc7530` in one branch. This reinforces keeping both name paths distinct during observation.

## Interpretation, confidence and unknowns

High confidence for the decoded selection and string-storage operations above. Moderate confidence for the SceneStack/UIScene/ScreenView mapping from multiple independent literals, tables, thunks and known callback signatures. **No confidence claim for observed screen transitions yet:** these are static results.

Proposed reporting rule, pending live validation: report the final scene selected by the native stack's own accessor, and exclude qualifying background layers from element counting. That choice is explicit and reproducible; whether it matches the player's foremost actionable screen must be checked during modal transitions. The main/client/composite stack ownership relationship, primary-client selection, pending transition semantics and native thread affinity remain unresolved. No heap address is retained from earlier sessions.

## Live validation and Milestone A integration (supersedes static-only status)

The supported game was subsequently launched using `BedrockOnLinux play`. The matching Windows Frida 17.23.2 server and disposable probe gate succeeded; each observation detached normally and cleaned up its own helpers. The F3 DLL was auto-injected by the launcher. Game PID, heap addresses and transport endpoints in the ignored captures are session-specific and are not reused by client code.

Four bounded captures were used:

- `live-01`: `0x567520` received zero calls. `0x56d000` ran naturally and returned an empty global-stack result. Initial per-thread throttling could miss a second stack on the same thread; this was corrected to throttle per stack, rather than interpreting the empty result as the active UI.
- `live-02`: bounded hooks on `0x4ccf520`/`0x4cc7530` identified `start_screen`, `debug_screen`, and `toast_screen` rendering concurrently on thread 280. The start menu's produced name was `start_screen`. This rejects a last-rendered-scene selection rule. This alternate experiment remains local; it is not part of the DLL.
- `live-03`: corrected per-stack `0x56d000` observation separated caller RVA `0x65b0119` (player/client stack) from `0x8871cd` (global toast stack). Native results on the player stack were `hud_screen → pause_screen → hud_screen → inventory_screen`. The underlying scene entry changed and stack depth moved between 3 and 4. Normal Escape/E input and game-only screenshots corroborated gameplay, Pause and Inventory. The toast stack independently returned `toast_screen` and was excluded.
- `live-04`: the player-stack native result was `small_chest_screen`; the visible chest interface was the BeHub resource pack's custom server list. Its runtime root-control name was also `small_chest_screen`. Closing it returned `hud_screen`, opening Pause gave `pause_screen`, and opening Settings gave `ui://./hbui/index.html` with a different native scene table (`0xf220000`). This URI is a genuine native identifier for that Ore UI scene, not a guessed settings-screen name. It does not expose the individual web route.

All observed native screen callbacks above ran on Windows thread **280**, matching this session's independently armed native reload frame thread. Absolute thread IDs are not compiled into the DLL. Raw events, screenshots, original-bound TSV selections, decompiler output and source/DLL checkpoints remain under `.local/re-investigation/screen-metrics-20261106/`.

Static follow-up of native caller interval `0x65b00b0–0x65b028d` shows an object virtual call through `+0x738` obtaining a guarded stack view, then its virtual `+0x160` returning the name at call site `0x65b0119`. The global path in `0x886da0–0x887654` calls through a different guarded view and reaches `0x56d000` from `0x886f93`/`0x8871cd`. This explains why a concrete SceneStack table alone cannot select the active player UI. `0x11d1f0` was also decompiled: it concatenates the two string arguments without introducing a namespace separator; the exact caller-produced controller suffix must not be reinterpreted as a JSON namespace.

The DLL now observes the original `0x56d000` invocation, copies its native-produced string **after** the original returns and **before** its caller regains control, and accepts only caller `0x65b0119` on the currently verified reload/game thread. The original function remains responsible for native allocation, reference management and destruction; Conduit never constructs or destroys an MSVC game string. The optional screen hook is created/enabled separately after required reload hooks activate; inability to install it does not disable reload. Hook code and state remain pinned/resident with the existing backend lifecycle.

Sampling is at most four times per second, uses guarded `ReadProcessMemory` copies of a 32-byte string descriptor and at most 192 name bytes, validates the concrete stack table, and stores no game pointers. A diagnostic sample publishes with `try_lock`; it skips a contended publication rather than blocking the game thread. The overlay takes a short lock to copy the fixed-size text only. No mutex spans the original native call. Empty/invalid/oversized names invalidate the sample; a sample expires after one second without refresh. Split-screen/multiple registered clients disable the thread gate, so this first milestone reports unavailable there. No control-tree traversal or JSON UI namespace inference is enabled.

The reporting rule is now: **the final scene selected by the naturally executing primary player/client stack name request**, excluding the independent global toast/debug stack. This may be a legacy identifier or a native web UI URI. It is not an aggregate of every visible layer and not a label inferred from the resource pack. A BeHub replacement can correctly retain `small_chest_screen` as its native identity.

Changed client files: `src/experimental/legacy_reload.cpp/.hpp` (optional observation and verified-thread gate), `src/core/screen_metrics.hpp` (copied expiring text), `src/platform/windows/debug_overlay.cpp/.hpp` and `src/standalone/entry.cpp` (existing field binding only). The renderer, F3 handling, presentation FPS and reload implementation are retained. Tests cover copy ownership, freshness/expiry, invalidation, rejected names, concurrent access, and the actual overlay text binding; strict image/configuration guards remain tested. Element counting and separate JSON definition/root identification are deliberately deferred to the next user-approved milestone.
