# Main-menu logo investigation — incomplete

Target: Bedrock Windows GDK x64 **1.26.60.5**, package **1.26.6005.0**,
2026-11-08. REA `open_binary` identified the installed executable as PE x86_64
with SHA-256 `1d6ad5c217e9305442c353ba3e9bca623d5719134e1cc8a84fb1233f7145e85c`.
The resolved artifact was the BedrockOnLinux `games/release/1.26.60.5/`
`Minecraft.Windows.exe`. This is the same image documented by the existing
native integration; none of the following establishes another supported build.

## Question and method

Can the single main-menu logo image be changed without replacing a shared
texture, changing game files, or affecting resource-pack-customized titles?
Reviewed the existing [frontend selection](1.26.60-menu-screen.md),
[control traversal](1.26.60-ui-controls.md), and
[native rendering](1.26.60-native-debug-rendering.md) evidence. Inspected the
installed vanilla resource inventory and the local PNG. Opened the original
image through REA/Hopper, then requested a literal `title_screen` string search.
The provider timed out at bridge startup after 120 seconds, before producing
string results. This is a tooling failure, not a negative string-search result.
The target was closed after the failed query. No live attach or memory mutation
was performed for this investigation. The requested reference screenshot was
not attached to this chat.

## Observations and interpretation

- Prior naturally observed frontend selection proves the default title uses a
  legacy scene with runtime root `start_screen`, scene table RVA `0xf20ec60`,
  and an empty player stack. Play transitions to the distinct HBUI scene table
  `0xf220000`. Those are exact-image observations from the linked investigation,
  not evidence that every logo with this root is the vanilla title logo.
- The current image's vanilla resource pack stores UI definitions in
  `data/resource_packs/vanilla/__brarchive/ui.brarchive`; no loose
  `ui/start_screen.json` was present. `contents.json` lists
  `textures/ui/title.png`. A listed texture path does not establish which
  control references it or whether other screens share it. The archive format
  was not decoded here.
- The existing native renderer verifies text submission and filled rectangles.
  It establishes no image-component setter, PNG decoder, texture upload,
  image draw ABI, texture lifetime, or title-control ownership contract.
- `assets/logo.png` is 153,289 bytes, PNG RGBA, 2004 by 686, SHA-256
  `3d2b75a9f89f0a0c8b2f83c103e97d7bc2b011ae73a734fe857440836bc759ef`.
  A bounded local walk checked all PNG chunk lengths and CRCs through IEND.
  This does not verify decoding by Minecraft or visual scaling.

Confidence is high that the default title participates in the existing legacy
UI path. The exact logo control, image source mutation ABI, definition origin,
and scoped texture lifetime remain **unverified**. A native renderer or custom
resource-pack control could still supply the visible logo; the current evidence
does not distinguish those alternatives.

## Client impact and blocker

The experimental DLL packages the PNG as resource 104 (`RCDATA`) using
`src/standalone/logo.rc.in`. `src/standalone/logo_resource.cpp` exposes a borrowed
byte span and dimensions with bounded resource size, PNG signature, and IHDR
checks. It opens no runtime filesystem path and creates no GPU/game resource.
The accessor does not decode pixels or validate compressed data; a future
decoder must reject invalid payloads and retain the original logo on failure.

**Logo replacement remains disabled.** Packaging is complete, rendering is not.
No texture hook, control patch, guessed screen-name gate, layout change, or
global override is installed. The original Minecraft logo remains visible.

To proceed safely, recover the title definition and observe its actual image
component during natural UI callbacks. Prove active frontend ownership, control
identity/type, and the vanilla definition/resource origin together; a copied
screen label alone cannot provide that gate. Establish a scoped image setter
and game-owned texture lifetime, restoration before scene destruction/shutdown,
and a way to reject customized title definitions. Record exact-image signatures
and ownership evidence before enabling the compatibility feature.

Manual validation must compare vanilla title before/after, splash text and
buttons, GUI scaling/aspect ratio, transitions through Play/Settings, world
loading, HUD, return to title, a pack-customized title, repeated Ctrl+R, and
deactivation. No native visual behavior is claimed verified by compilation or
resource inspection.

## Follow-up investigation — 2026-11-09

**Root cause established:** v0.4.0-beta packages the logo but implements no
replacement/rendering path. `embeddedLogo()` has a declaration and definition
but no caller (`rg -n 'embeddedLogo|mainMenuLogo' src`). The sole compatibility
profile has `mainMenuLogo=false`; that flag is not consumed by a logo renderer.
The existing native renderer submits text and filled rectangles only. Changing
the flag alone would therefore do nothing. This is an incomplete feature, not
a missing runtime PNG or a failed attempt to replace the image.

REA `inspect_pe_resources` inspected the actual published DLL, SHA-256
`f7024e36f67448e1ef2b32cae77e119fb62240762ceafaeec3cee9119ca76302`.
Evidence `ev_942b6fcb012f6b1da6a0f0ebb0af3ff1732465a1548312f85d0e8b6a81b7926a`
confirms RCDATA 104, language 1033, 153,289 bytes, and PNG payload SHA-256
`3d2b75a9f89f0a0c8b2f83c103e97d7bc2b011ae73a734fe857440836bc759ef`.
Resource-table observation establishes packaging, not image decoding or drawing.

### New packaged-definition evidence

The earlier statement that the archive was not decoded is superseded: bounded
local inspection found plaintext JSON documents inside the archive. No game
files were modified. The installed executable was rehashed and still matches
the verified 1.26.60.5 image above. Two carriers were inspected separately:

| Carrier | SHA-256 | `start` JSON byte offset | `common_art` JSON byte offset |
| --- | --- | --- | --- |
| `ui.brarchive.bol-orig` | `8d13e053654e3a832c7a99fe6f4ef53af1798ae474731036a127fef17638b1c5` | 2046272 | 2792053 |
| Installed `ui.brarchive` | `f9b0809cd94d987e0fb7ae0560070020389580138ca74dfb3aa67409b07a2d52` | 2046272 | 2792080 |

Reproduction: read the selected carrier as bytes, locate the exact markers
`{"namespace":"start"` and `{"namespace":"common_art"`, then use Python
`json.JSONDecoder().raw_decode()` on the UTF-8 suffix at each marker. This is
focused document recovery, not a complete archive-format parser. The selected
fields below match in both carriers; other archive content was not compared.
The original backup's provenance is its local filename, not an independently
verified distribution checksum. Do not attribute the installed archive's
unrelated differences to Conduit.

Observed definition chain:

1. `start.start_screen_content` references the main buttons/title stack.
2. `start.main_buttons_stack_panel` instantiates
   `title_panel_content@common_art.start_title_panel_content`.
3. Its Windows branch selects `common_art.title_panel_win10`.
4. That panel instantiates `title_image@common_art.title_image`.
5. The image definition has type `image` and source `textures/ui/title`.

The Windows title panel is anchored top-middle with offset `[0,"10%"]` and size
`["55%","18.85%x"]`. Splash text is a separate sibling using
`splash_text_renderer`. Crucially, `common_art.pause_logo_panel` also selects
`common_art.title_image` in its Windows branch. Therefore replacing the shared
texture or shared definition would affect at least another screen. The scoped
mutation must apply to the live title instance, retaining the separate splash
control and respecting customized definitions.

This is high-confidence static evidence for the default legacy JSON UI path;
it does not establish the current runtime instance, image component ABI, texture
creation/import mechanism, setter, restoration or ownership. Those remain the
implementation blocker. No addresses or game mutations were guessed.

## Implemented and visually observed — 2026-11-09

The blocker above is superseded for the exact supported build by the verified
[image submission/import ABI](1.26.60-image-submission.md). A bounded live import
loaded `assets/logo.png` through RawPath and later reported 2004×686 pixels.
REA evidence: `ev_862e50cf2c3824e3a633a54fb2003eabc07d9502eee3902e626f6b9a28aaae6a`.
An initial Frida call used a boolean where its integer marshaller expected an
integer and was rejected before texture loading; passing the native low-byte
flag as an integer corrected the probe. No crash was observed.

A 30-second prototype changed only the selected title sprite draw's image
argument, rectangle and UVs. It rendered the intended logo, then detached and
restored normal drawing: evidence
`ev_d721d9839c03041422c760dc1e97c23418435e0f1a2028dbc7604ea0b70c31fa`.
This established the rendering mechanism before implementing the DLL path.

The standalone implementation now:

- Materializes its embedded PNG into a private `ConduitClient/cache/` file and
  uses Minecraft's native loader. Users do not distribute a separate PNG.
- Borrows the current owner only during the original natural owner-frame call.
  Live observation established that ScreenView render is nested in this call
  on thread 280. The gate freshly checks the single client, empty player stack,
  frontend stack top, exact scene class and scene/view identity; it never
  dereferences a cached owner outside that borrowed lifetime.
- Additionally requires a legacy visual tree with root `start_screen`, exact
  sprite implementation, owning control `title_image`, original source
  `textures/ui/title` in filesystem 0 and original image dimensions 1937×333.
- Conservatively suppresses replacement when recognized profile metadata lists
  any global pack, is invalid, or no initialized profile can be identified.
  An initialized profile with no global stack file represents the vanilla
  default. Checks run on the worker every 250 ms, not during native rendering.
  This is an on-disk customization guard, not recovered native pack provenance;
  dynamic customization transitions still require manual validation.
- Waits for the imported image to become ready with the expected dimensions.
  Until then, or if any guard fails, it calls the original draw unchanged.
- Contains the PNG in the original rectangle, preserving aspect ratio and
  center, with full-image UVs. Splash text and buttons are separate draws.
- Retains one bounded native resource descriptor and owning texture result in
  the already pinned module for deferred-render safety. Disabling stops
  substitution/hooks; these native references remain until process exit.

The compiled standalone DLL, copied under a fresh `ConduitLogoFix.dll` filename,
was loaded only after the previous client reported Disabled (phase 4).
The old client's Ctrl+K focus gate ignored synthetic X11 input because Wine
reported Explorer as foreground, so its supported DISABLE sentinel was used
instead; only our temporary sentinel was removed afterward. This is not a new
native Ctrl+K verification.

The new DLL logged `Title logo rendered using native texture import` and the
captured game window showed the correct Conduit Client logo with the splash and
menu buttons intact. Frida was then detached and its owned helper stopped.
A fresh capture still showed the replacement, proving that the DLL supplies it
without a continuing instrumentation script. Local captures:
`live/title-dll.png`, `live/title-standalone-final.png`; source evidence:
`live/rea-session-evidence.json`, all under the ignored investigation directory.
The game was left running with the experimental fix active.

Automated results: 11/11 portable tests; all 24 Windows/Wine checks passed
across the full run and an isolated rerun. The initial desktop overlay smoke
lost focus during a factory-update assertion; rerunning just that test under
Xvfb 1280×1024 passed. New tests cover image eligibility, invalid geometry,
aspect ratio, hash construction, embedded asset extraction/cache repair, and
customization metadata rejection.

Confidence: direct live evidence for this title screen and DLL implementation.
Synthetic X11 clicks did not navigate Settings; do not count that capture as
another-screen validation. World/loading/pause/custom-pack transitions, repeated
reload and new-module deactivation remain manual regression requirements. No
installation file or pack was modified; no release, tag or GitHub asset was
updated by this fix.
