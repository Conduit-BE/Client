## Question and method

texture, changing game files, or affecting resource-pack-customized titles?
Reviewed the existing [frontend selection](1.26.60-menu-screen.md),
[control traversal](1.26.60-ui-controls.md), and
[native rendering](1.26.60-native-debug-rendering.md) evidence. Inspected the
installed vanilla resource inventory and the local PNG. Opened the original

The provider timed out at bridge startup after 120 seconds, before producing
string results. This is a tooling failure, not a negative string-search result.
The target was closed after the failed query. No live attach or memory mutation
was performed for this investigation. The requested reference screenshot was
not attached to this chat.

## Observations and interpretation

- Prior naturally observed frontend selection proves the default title uses a
  legacy scene with runtime root `start_screen`, scene table RVA `0xf20ec60`,
  and an empty player stack. Play transitions to the distinct HBUI scene table
  `0xf220000`. Those are exact-image observations from the linked investigation,
  not evidence that every logo with this root is the vanilla title logo.
- The current image's vanilla resource pack stores UI definitions in
  `data/resource_packs/vanilla/__brarchive/ui.brarchive`; no loose
  `ui/start_screen.json` was present. `contents.json` lists
  `textures/ui/title.png`. A listed texture path does not establish which
  control references it or whether other screens share it. The archive format
  was not decoded here.
- The existing native renderer verifies text submission and filled rectangles.
  It establishes no image-component setter, PNG decoder, texture upload,
  image draw ABI, texture lifetime, or title-control ownership contract.
- `assets/logo.png` is 153,289 bytes, PNG RGBA, 2004 by 686, SHA-256
  `3d2b75a9f89f0a0c8b2f83c103e97d7bc2b011ae73a734fe857440836bc759ef`.
  A bounded local walk checked all PNG chunk lengths and CRCs through IEND.
  This does not verify decoding by Minecraft or visual scaling.

Confidence is high that the default title participates in the existing legacy
UI path. The exact logo control, image source mutation ABI, definition origin,
and scoped texture lifetime remain **unverified**. A native renderer or custom
resource-pack control could still supply the visible logo; the current evidence
does not distinguish those alternatives.

## Client impact and blocker

The experimental DLL packages the PNG as resource 104 (`RCDATA`) using
`src/standalone/logo.rc.in`. `src/standalone/logo_resource.cpp` exposes a borrowed
byte span and dimensions with bounded resource size, PNG signature, and IHDR
checks. It opens no runtime filesystem path and creates no GPU/game resource.
The accessor does not decode pixels or validate compressed data; a future
decoder must reject invalid payloads and retain the original logo on failure.

**Logo replacement remains disabled.** Packaging is complete, rendering is not.
No texture hook, control patch, guessed screen-name gate, layout change, or
global override is installed. The original Minecraft logo remains visible.

To proceed safely, recover the title definition and observe its actual image
component during natural UI callbacks. Prove active frontend ownership, control
identity/type, and the vanilla definition/resource origin together; a copied
screen label alone cannot provide that gate. Establish a scoped image setter
and game-owned texture lifetime, restoration before scene destruction/shutdown,
and a way to reject customized title definitions. Record exact-image signatures
and ownership evidence before enabling the compatibility feature.

Manual validation must compare vanilla title before/after, splash text and
buttons, GUI scaling/aspect ratio, transitions through Play/Settings, world
loading, HUD, return to title, a pack-customized title, repeated Ctrl+R, and
deactivation. No native visual behavior is claimed verified by compilation or
resource inspection.
