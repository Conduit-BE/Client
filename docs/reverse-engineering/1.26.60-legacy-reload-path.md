# Legacy JSON UI reload: static findings

2026-11-05; Bedrock release **1.26.60.5**, package **1.26.6005.0**, Windows x64 executable analyzed entirely on Linux x64. Installation/version identification and original SHA-256 are recorded in [the original note](1.26.60-json-ui.md). The original executable remains SHA-256 `1d6ad5c217e9305442c353ba3e9bca623d5719134e1cc8a84fb1233f7145e85c`.

Scope: legacy `_ui_defs.json` only. No game execution, attachment, or injection occurred during this follow-up. No Conduit implementation, launcher settings, or global REA registration was changed.

## Result and stopping point

There is strong static evidence of an intended legacy UI reload action: `button.reload_ui_definitions` is associated with a callback that calls a nontrivial action routine. Separately, concrete functions load `ui/_ui_defs.json`, process `ui_defs`, and perform refresh-like collection operations.

**The remaining concrete blocker is joining those branches through indirect dispatch.** The action obtains objects and calls through loaded function pointers. Their concrete dynamic targets and owning instances have not been established. Consequently this is a candidate reload path, not an integration-ready API. No function name, C++ type, calling convention, or vtable layout is asserted from the addresses below. Synthetic Ghidra `FUN_...` names are not recovered symbols.

## First indirect call in `0x6583170`: provenance follow-up

Read-only query of the existing Ghidra project, without re-analysis or decompilation; output retained at `.local/re-investigation/legacy-first-indirect.txt`.

The first call is at RVA `0x65831b1`. Its target-register provenance is:

```text
0x6583184  RSI = incoming RCX
0x65831a3  RCX = [RSI + 0x10]       ; object O
0x65831a7  RAX = [RCX]              ; dispatch table V
0x65831aa  RAX = [RAX + 0x270]      ; intended target T
0x65831b1  call [static VA 0x14f99ef70]
```

The saved image's last pointer contains static VA `0x14eea5440`; its instruction is `jmp rax`. This confirms register-preserving dispatch, not a resolved UI operation. The meaningful target is `T = qword[qword[O] + 0x270]`.

The existing callback supplies the missing object through its incoming **R8 register**: at RVA `0xf20479` it stores R8 at `[RBP-0x10]`, then passes `RCX = RBP-0x20` to `0x6583170`. Therefore `[incoming RCX+0x10]` in the action is that callback-supplied object, rather than a statically known global. No concrete dispatch-table assignment to that object is established in the available caller evidence.

The known table entry at static VA `0x14f091bd0` does contain `0x14083a190`, the legacy definition-loader candidate. This does **not** resolve the first call: nothing establishes that the callback's incoming object has that table, nor that this getter returns its owner.

Stopping point: the target expression is confirmed, but its object/table value remains unbound. Resolving it requires static construction/dispatch provenance for the callback's incoming R8 object. This is a bounded evidence gap, not proof that static resolution is inherently impossible. No later indirect call was followed and no runtime experiment or client change was made.

## Callback R8 origin: registration and invocation

Additional bounded inspection reused the saved Ghidra project. Only two new functions were decompiled: original RVA `0x41c190` and insertion helper `0x434d30`. Captures, filtered assembly and caller lists are under `.local/re-investigation/r8-origin/`. No implementation changes or runtime access occurred.

**Registration does not capture the eventual R8 object.** The existing `0x420d30` hashes the event name and inserts the callable into the registry at its incoming object's `+0x18`. Helper `0x434d30` stores the hash at node `+0x20`, flags at `+0x28`, callable storage at `+0x30`, and the active callable pointer at `+0x68`. These are observed stores, not asserted C++ layouts.

**Invocation supplies context separately.** Function `0x41c190–0x41ff2e` selects a matching-hash node from a registry tree (including the tree at object `+0x18`). At `0x41f6cd` it loads the node's callable pointer from `+0x68`, loads its dispatch entry at `+0x10`, and calls through the guard at `0x41f6ef`, with R8 loaded from `[RBP+0x100]`. For the registered callable, the associated table entry is the already identified `0xf203e0`.

That selected context has two observed sources:

- Default/fallback: the dispatcher's incoming R8, saved at `0x41c1e3`. Assignments at `0x41d7d4` / `0x41d858` place it in the context local used at invocation.
- Conditional override: the dispatcher searches an object-held collection and obtains another pointer at `0x41daa4` (`RAX = [RCX+0x28]`, where RCX is the selected record). Nearby reference-count acquisition and fallback support a weak-reference-lock interpretation. No concrete class or table is established by those operations. The fifth incoming argument controls whether this lookup is attempted.

The validated direct caller of `0x41c190` is `0xed3bd0`, at `0xed3c47`. It forwards `R8 = [incoming_R8_wrapper+0x10]` at `0xed3c39`, using the same owner field `+0x20` for the registry that registration uses.

One direct caller of this forwarding routine was found and instruction-validated: function `0x88aef0–0x88b1a8`, call `0x88afc3`. It supplies a stack wrapper at `[RBP+0x88]`. Immediately before that, `0x88af93–0x88afa6` requests that wrapper through an indirect operation:

```text
RCX = incoming_owner + 0x30
RAX = qword[RCX]
RAX = qword[RAX + 0x38]
RDX = address of stack wrapper
call guard_dispatch                 ; RVA 0x88afa6
```

**Updated evidence boundary:** the default callback context comes from this indirect wrapper producer; the override context comes from a selected external record. Neither source currently has a proven concrete dispatch-table value. The code-pointer table observed in another constructor is insufficient to bind the incoming owner here. Consequently no concrete type/vtable for callback R8 is claimed, and the first target in `0x6583170` remains unresolved. Further progress requires proving this producer's actual table or the selected override record's construction, rather than assigning a type from nearby addresses. Investigation stops at that boundary.
